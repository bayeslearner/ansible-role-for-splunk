# Requirements: Molecule virtual lab

## Scope

The Docker and Molecule harness under `testing/`: images, the Taskfile entry point, the `infra`, `day0` and `day1` Molecule scenarios, the `small`, `prod` and `dev` topologies, the controller with its web terminal, and the Gitea server. This sprint makes the harness verified and portable to the two hosts it will run on (`docs/steering/product.md`, Where The Lab Runs). Day 2 operations are `10-day-2-operations`.

## Glossary

- **Virtual lab:** the set of containers on `splunk-test-network` that stand in for a Splunk estate, plus the controller that deploys to them.
- **Controller:** container `ansible-controller`, the deployment box an operator logs into. It runs Ansible over SSH against the lab nodes.
- **Runner:** container image `molecule-runner`, which runs Molecule and creates containers through the host's Docker socket. Started per command (`--rm`) or kept as `mol-run`.
- **Node:** a systemd container (Ubuntu 22.04 or AlmaLinux 9) that receives Splunk.
- **Topology:** one of `testing/molecule/environments/{small,prod,dev}`, chosen with `MOLECULE_ENV`.
- **Scenario:** a Molecule scenario directory (`infra`, `day0`, `day1`), each a lifecycle stage.
- **Lab host:** the Docker host the lab runs on: a Mac with OrbStack, the pve2 VM, or `splunkapp-preprod01`.

## Mental Model And Invariants

- Model (Kun, recorded in project memory 2026-03-30 and the README): the lab is a realistic deployment box first and an automated test second. Molecule is "the vehicle, not the brain": it creates and destroys infrastructure and stays invisible from inside the controller.
- Invariant: the lab deploys Splunk through the role's real entry points (`deployment_task`, `splunk_download_local`), never a lab-only path into the role.
- Invariant: a playbook and inventory that work through Molecule also work from the controller with no extra flags.
- Invariant: `testing/Taskfile.yml` is the only entry point; `run-tests.sh` forwards to it.
- Invariant: secrets are generated per checkout into `testing/.secrets/` and never committed.

## Requirements

### R1. One-command setup
WHEN an operator runs `task setup` on a lab host, THE Taskfile SHALL generate missing secrets, build missing images, download the Splunk Enterprise and Universal Forwarder tarballs for the selected topology's version, create `splunk-test-network`, and start the runner, and SHALL skip each step whose result already exists.

### R2. Topology selection
WHEN `MOLECULE_ENV` names a topology, THE scenarios SHALL build and deploy exactly the hosts that topology's `hosts.yml` lists, with the image each host's `docker_image` names.

### R3. Infrastructure stage
WHEN `task infra:setup` runs, THE `infra` scenario SHALL start every topology host as a systemd container on `splunk-test-network`, install the lab SSH key for user `ansible` on every node, and leave the controller able to reach every node over SSH.

### R4. Day 0 install
WHEN `task day0:test` runs after R3, THE `day0` scenario SHALL install Splunk on every `full` and `uf` host through the role with `deployment_task: check_splunk.yml`, distributing the pre-downloaded tarball from `testing/software`, and SHALL report service, port and cluster state.

### R5. Day 1 operations
WHEN `task day1:test` runs after R4, THE `day1` scenario SHALL restart Splunk through the role (`splunk_restart.yml`), check status through the role (`check_splunk_status.yml`), and fail unless each host's Splunk service is active.

### R6. Controller as a deployment box
WHEN an operator opens a shell on the controller after R3, THE controller SHALL have `ansible.cfg` with the secrets, common and topology inventories and `roles_path=/workspace/roles`, so `ansible all -m ping` and `ansible-playbook /workspace/playbooks/<playbook>.yml` run with no flags.

### R7. Web terminal
WHEN the lab is up, THE controller SHALL serve a password-protected terminal for user `ansible` at `http://<lab host>:3000/ttyd`.

### R8. Git server for app deployment
WHEN the `prod` topology is up, THE lab SHALL run a Gitea server reachable as `git-server` that holds the app repositories the topology's `git_apps` name.

### R9. Workflows and cleanup
`task workflow:full` SHALL run infra, day0, day1 and destroy in order and stop at the first failure; `task workflow:quick` SHALL leave the lab running after day0; `task reset` SHALL remove every container, volume and network the lab created and nothing else.

### R10. Portability
THE lab SHALL run unchanged on macOS with OrbStack, on a Linux x86_64 Docker host (the pve2 VM), and on `splunkapp-preprod01`.

## Non-Functional Requirements

- **Isolation on a shared host:** on `splunkapp-preprod01` the lab must not give lab users control of the host, must not expose open services beyond what the operator chooses, and must not resolve lab names to real hosts.
- **Reproducibility:** a fresh lab host builds the same images and toolchain on any day (pinned bases, packages and collections).
- **Fidelity:** the Ansible version that runs the role from the controller matches the one Molecule uses, or the difference is stated.

## Out Of Scope

- Day 2 operations (`10-day-2-operations`).
- Changes to the role itself, except fixes the lab exposes, which go upstream separately.
- Twingate access (`.env.example` mentions it; nothing implements it).
